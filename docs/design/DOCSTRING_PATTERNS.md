# Docstring Patterns and Guidelines

This guide provides principles and guidelines for writing docstrings in Dart code to ensure consistent, readable, and properly formatted documentation that displays correctly in IDE hover boxes.

## Overview

Docstrings in Dart use triple-slash comments (`///`) to document classes, methods, properties, and other public APIs. When written with proper formatting, these docstrings appear in IDE hover boxes, autocomplete suggestions, and generated documentation. Proper formatting ensures that multi-line docstrings display correctly with appropriate line breaks.

## Formatting Requirements

### Basic Format

All docstrings must use triple-slash comments (`///`) and follow this pattern:

**Single-line docstring:**
```
/// Brief description of the item.
```

**Multi-line docstring:**
```
/// First line of description
///
/// Second line of description
///
/// Additional paragraphs as needed
```

### Critical Rule: Blank Lines Between Paragraphs

When writing multi-line docstrings, **always include a blank `///` line between consecutive lines of text**. This ensures proper line breaks when viewing docstrings in IDE hover boxes.

**Correct:**
```
/// Widget representing a single currency option
///
/// Shows currency flag, name, symbol, code, and selection indicator
```

**Incorrect:**
```
/// Widget representing a single currency option
/// Shows currency flag, name, symbol, code, and selection indicator
```

The incorrect format will display as a single line in IDE hover boxes, making it difficult to read.

## What Should Have Docstrings

### Required Documentation

All public APIs should have docstrings:

1. **Public Classes** - Every public class (not starting with `_`) should have a docstring explaining its purpose
2. **Public Methods/Functions** - All public methods should document their purpose, parameters, and return values
3. **Abstract Methods** - Methods in abstract classes/interfaces should have docstrings
4. **Public Properties** - Significant public properties should have docstrings
5. **Enums** - Public enums should have docstrings
6. **Extensions** - Public extensions should have docstrings

### Optional Documentation

These items may have docstrings but are not strictly required:

1. **Simple Constants** - Constants in constant classes may rely on class-level documentation
2. **Private Classes/Methods** - Internal implementation details may omit docstrings
3. **Generated Code** - Code generated by build_runner, freezed, etc. does not need docstrings

## Docstring Structure

### Class Docstrings

Class docstrings should explain:
- What the class represents or does
- When to use it
- Key characteristics or behaviors

**Format:**
```
/// Brief one-line description
///
/// More detailed explanation of the class purpose, usage, and key features.
/// Additional paragraphs as needed for complex classes.
```

### Method Docstrings

Method docstrings should explain:
- What the method does
- Parameters (using `[paramName]` format)
- Return values
- Exceptions or error conditions
- Side effects if any

**Format:**
```
/// Brief description of what the method does
///
/// [paramName] - Description of the parameter
///
/// [anotherParam] - Description of another parameter
///
/// Returns description of return value
///
/// Throws description of exceptions if applicable
```

### Property Docstrings

Property docstrings should explain:
- What the property represents
- Its type and constraints
- When it's used or set

**Format:**
```
/// Brief description of the property
///
/// Additional details if needed, such as constraints, default values, or usage notes
```

## Usage Guidelines

### When to Use Multi-line Docstrings

Use multi-line docstrings when:
- The description requires more than one sentence
- You need to document multiple parameters
- You need to explain complex behavior or edge cases
- You want to provide usage examples or notes

### When Single-line is Sufficient

Use single-line docstrings when:
- The purpose is self-explanatory from the name
- A brief one-sentence description is sufficient
- The item is simple and doesn't require detailed explanation

### Parameter Documentation

When documenting parameters, use the `[paramName]` format:

```
/// [email] - User's email address
///
/// [password] - User's password
```

This format is recognized by Dart's documentation tools and appears correctly in IDE hints.

### Return Value Documentation

Always document return values, especially for methods that return complex types or nullable values:

```
/// Returns the token if found, null otherwise
```

```
/// Returns AuthResponse with token and user info on success
///
/// Returns Failure on error (network, server, or unknown)
```

## Best Practices

### 1. Consistency

Use consistent formatting and style throughout the codebase:
- Always use triple-slash comments (`///`)
- Always include blank lines between paragraphs
- Use consistent parameter documentation format
- Maintain consistent level of detail

### 2. Clarity

Write clear, concise docstrings:
- Start with a brief, one-sentence summary
- Use simple, direct language
- Avoid unnecessary jargon
- Be specific about behavior and constraints

### 3. Completeness

Document all important aspects:
- Document all public APIs
- Include parameter descriptions
- Document return values
- Note exceptions or error conditions
- Explain side effects if any

### 4. Accuracy

Keep docstrings accurate and up-to-date:
- Update docstrings when code changes
- Ensure descriptions match actual behavior
- Remove outdated information
- Fix inaccuracies promptly

### 5. Formatting

Maintain proper formatting:
- Always include blank `///` lines between paragraphs
- Use consistent indentation
- Follow the established patterns
- Ensure proper line breaks

### 6. Context

Provide appropriate context:
- Explain the purpose and usage
- Document relationships to other classes
- Note dependencies or requirements
- Include relevant examples or notes

## Common Patterns

### Class Pattern
```
/// Brief description of the class
///
/// More detailed explanation of purpose, usage, and key characteristics.
/// Additional context or notes as needed.
```

### Method Pattern
```
/// Brief description of what the method does
///
/// [param1] - Description of first parameter
///
/// [param2] - Description of second parameter
///
/// Returns description of return value
```

### Property Pattern
```
/// Brief description of the property
///
/// Additional details about constraints, usage, or behavior
```

### Abstract Method Pattern
```
/// Brief description of the method
///
/// [param] - Description of parameter
///
/// Returns description of return value
///
/// Throws description of exceptions
```

### Provider Function Pattern
```
/// Brief description of what the provider provides
///
/// Additional details about dependencies, initialization, or usage
```

## Formatting Checklist

Before committing code, verify docstrings follow these rules:

- [ ] All public classes have docstrings
- [ ] All public methods have docstrings
- [ ] All abstract methods have docstrings
- [ ] Multi-line docstrings have blank `///` lines between paragraphs
- [ ] Parameters are documented using `[paramName]` format
- [ ] Return values are documented
- [ ] Exceptions are documented where applicable
- [ ] Docstrings are accurate and up-to-date
- [ ] Formatting is consistent with the codebase

## IDE Display

Properly formatted docstrings will display correctly in:

- **Hover Boxes** - When hovering over a class, method, or property
- **Autocomplete** - In IDE autocomplete suggestions
- **Generated Documentation** - In documentation generated by dartdoc
- **Code Navigation** - When navigating through code

The blank `///` lines between paragraphs ensure that multi-line descriptions appear with proper line breaks, making them easier to read and understand.

## Decision Framework

When writing docstrings, consider:

1. **Visibility**
   - Is this a public API that others will use?
   - Should this be documented for external consumers?

2. **Complexity**
   - Is the purpose clear from the name alone?
   - Does it require explanation of behavior or constraints?

3. **Usage**
   - Will developers need guidance on how to use this?
   - Are there important considerations or gotchas?

4. **Context**
   - Does it relate to other classes or methods?
   - Are there dependencies or requirements to document?

5. **Maintenance**
   - Will the docstring help future maintainers?
   - Is the behavior non-obvious or complex?

## Examples

### Good: Properly Formatted Class
```
/// Service for secure storage operations
///
/// Provides encrypted storage for sensitive data such as tokens and credentials.
/// Uses platform-specific secure storage implementations.
```

### Good: Properly Formatted Method
```
/// Logs in with email and password
///
/// [request] - Login request containing email and password
///
/// Returns AuthResponse with token and user info on success
///
/// Returns Failure on error (network, server, or unknown)
```

### Good: Properly Formatted Property
```
/// JWT access token for authenticated requests
///
/// This token is used to authenticate API requests and should be stored securely.
```

### Bad: Missing Blank Lines
```
/// Widget representing a single currency option
/// Shows currency flag, name, symbol, code, and selection indicator
```

This will display as a single line in IDE hover boxes.
